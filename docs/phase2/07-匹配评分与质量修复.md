# 岗位匹配：评分与质量修复

> 状态：已上线（报告协议 `job-match-report-v3`，迁移 V79）。已在开发环境用真实模型（gpt-6.1-sol）走完“分析 → 澄清 → 追问一轮 → 最终报告”全流程。

## 1. 为什么要改

上一版的匹配报告有四个问题：

- 分数是关键词重合度，并不说明是否符合要求；
- “经验”“成长成本”等维度是按字数、字段名凑出来的；
- 可信度没有依据；
- 用户回答澄清问题后，回答内容没有进入评分。

用户看到 80 分，但说不清这 80 分从哪来。这一版的原则：**分数只由每条岗位要求的判定算出，每个判定都要有出处。**

## 2. 评分规则

### 2.1 逐条判定

模型对每条岗位要求给出四种判定之一，系统据此计算分数。模型自己不能给总分。

| 判定 | 含义 | 分值 |
| --- | --- | --- |
| MET 符合 | 简历或资料里有明确证据 | 100 |
| PARTIAL 部分符合 | 有证据，但不完整 | 60 |
| UNCLEAR 无法判断 | 信息不足 | 35 |
| NOT_FOUND 暂未发现证据 | 简历和资料里都没找到 | 0 |

- 判为 MET 或 PARTIAL，必须引用以下三者之一：简历字段（`resume:` 开头、在白名单里的路径）、已授权的资料，或用户对澄清问题的肯定回答。没有引用的，系统改判为 UNCLEAR。
- 引用了不存在的字段或资料，这条引用作废。
- 模型漏判的要求按 UNCLEAR 计。

### 2.2 权重

| 要求 | 权重 |
| --- | --- |
| 必须（MUST） | 3 |
| 重要（IMPORTANT） | 2 |
| 加分（BONUS） | 1 |
| 岗位职责（RESPONSIBILITY） | 1，计入“经验” |

岗位职责描述的是这份工作要做什么，并不是筛人的条件，所以权重最低。

总分 = 各条分值的加权平均。

### 2.3 维度

各维度按要求的类别分别计算。JD 里没有某类要求时，该维度显示“—”，不编数字。

- **核心技能**：技能类要求；
- **经验**：经验类要求，加上岗位职责；
- **学历与限制**：学历、地点等限制条件；
- **证据强度**：判为符合或部分符合的要求中，有简历或资料支撑的占比。只靠用户口头确认的不计入。

### 2.4 硬性门槛

硬性门槛只包括简历筛选时会直接卡人的条件：

- 学历和学位；
- 毕业届别（如“2026 届”）；
- 工作年限（如“3 年以上”“至少两年”）；
- 证书和语言成绩；
- 明确写了“必须”的要求。

“具备良好的沟通能力”“要求逻辑清晰”不算硬性门槛，按“重要”计。“至少一段实习”是“必须”，但不是硬性门槛。

### 2.5 投递建议

服务端先按以下规则算出建议上限：

| 条件 | 建议上限 |
| --- | --- |
| 任一硬性门槛判为“暂未发现证据” | 谨慎评估 |
| 总分 ≥ 75，且没有判为“无法判断”的硬性门槛 | 推荐投递 |
| 总分 ≥ 55 | 有条件投递 |
| 其余 | 先补强再投递 |

模型给出的建议只有不高于这个上限时才采用。模型给的理由只作文字展示。

### 2.6 可信度

可信度按“有依据的判定”占全部要求的比例计算：

- ≥ 75%：高；
- ≥ 50%：中；
- 其余：低。

“有依据的判定”指 MET 或 PARTIAL 有引用，或判为 NOT_FOUND。UNCLEAR 不算。

**规则预估**指 AI 不可用时的关键词粗估，可信度一律为低。

## 3. 澄清问题

### 3.1 选项判定

模型出题时给每个选项标出判定。例如“仅 SQL 有实际案例”标为部分符合，“尚无实际案例”标为暂未发现证据。

- 用户选定后，判定存入 `answer_verdict`。
- 下次分析时，评分直接读取这个判定，不再从选项文字里猜。
- 旧问题和系统自带的选项没有标注，按文字判断。例如“仅……”“只有其中……”判为部分符合，“尚无”“未涉及”“不属于”判为暂未发现证据。

### 3.2 回答对判定的影响

用户说自己只是部分具备或不具备时，即使简历里有相关字样，这条要求最高只判部分符合。

### 3.3 轮次限制

- 第一轮最多 5 个问题，之后最多追问一轮、3 个问题，然后出最终报告。
- 每次提交回答时，同一批回答的时间戳相同，系统据此计数轮次。
- 模型自带的“暂不确认……”选项会合并到统一的“暂不确认”里。
- 选项最长 60 字，超出的部分截掉，因为回答列宽为 64。

## 4. 其他修复

- **取消**：分析中途取消后，模型结果直接丢弃，不写报告，不扣额度，不发通知。所有状态更新都带 `status='ANALYZING'` 条件。
- **重新分析**：已取消、已暂停的匹配都可以重新分析，使用所选简历的最新版本。报告生成后简历又改过的，报告页会提示。
- **删除**：`DELETE /api/v1/job-matches/{id}` 归档匹配记录，历史页可以删除。分析中的记录不能删除。
- **隐私**：联系方式字段清单统一放在 `shared/privacy/ResumeContactFields`，简历分享和岗位匹配共用。清单补上了微信、QQ、各类链接、GitHub、LinkedIn、照片和姓名。
- **简历改写建议**：不合格的建议逐条丢弃，并记录日志，不再拖累整份报告。不合格指路径或原文不符、来源不在白名单、文字太短或重复。
- **通知**：需要澄清时，通知文案是“需要你确认几个问题”，不再说“报告已生成”。
- **统计**：平均分只统计已完成的匹配。“已优化简历”只统计在工作台里已经采纳的匹配建议。
- **AI 可用性**：`/api/v1/capabilities` 返回 `ai: {resume, jobMatch, careerPlanning}`，分别标出简历、岗位匹配、职业规划是否可用。不可用时，入口页显示提示，并禁用“开始”。

## 5. 真实模型检查记录（2026-10-19，gpt-6.1-sol）

检查用的样例是数据分析师校招 JD（10 条要求）和一份导入的简历。

| 步骤 | 结果 |
| --- | --- |
| 首次分析 | 约 60 秒。74–79 分，可信度高，8/10 条有依据。提出 3–4 个澄清问题 |
| 回答澄清 | “仅其中一项有充分实践”判为部分符合，并标为用户确认；“熟悉并独立完成过实际看板”把可视化加分项从无法判断提升为符合 |
| 追问轮 | 模型又提出 3 个新问题。修复前没有轮次上限，会一直追问下去 |
| 失败点（已修） | 简历改写建议质量不合格时整份报告暂停；规则预估显示“可信度高”；软技能被标为硬性门槛；选项“尚无实际案例”被当作符合；投递理由里出现“不据此安排学习计划”这类系统规则 |

## 6. 中断后的出路、导出与版本间的延续（2026-10-20）

### 6.1 暂停或取消之后

- **没有完成过报告的匹配**：仍停在分析页。暂停时可以“重试分析”（同一份输入）、“取消这次分析”或“查看规则预估”；取消后可以“重新分析”（回到确认步骤，使用最新简历）。
- **已有报告、重新分析没完成的匹配**：列表直接打开报告页，横幅说明最近一次分析的状态，并给出对应操作：
  - 进行中：查看进度；
  - 等待确认：去确认；
  - 暂停：重试或取消；
  - 取消：只做说明。
  报告仍是上一版。
- **重新分析期间旧报告的分数保持不变**：规则预估只在还没有任何 AI 报告时写入，所以列表上的分数和打开报告看到的一致。
- 匹配和列表接口新增 `reportVersions`，即已完成的 AI 报告数。

### 6.2 导出

- PDF 和 Word 的章节与报告页一致：概览（分数、可信度、有依据的条数、评分方式、摘要）、投递建议（含“已按分数调整”）、维度得分、硬性要求、逐条判定（优先级、判定、分值、依据来源、说明）、匹配优势、能力与材料缺口、简历修改建议、面试准备主题、提升计划（含完成进度）。
- 文件里不出现内部代码（如 MUST、NOT_FOUND）。
- 每次点击导出都重新生成文件。同一个请求编号再次提交时，如果之前的文件已过期（15 分钟），也会重新生成，不再返回失效的记录。

### 6.3 新版本延续用户已做的事

- **结论反馈**：同一条要求、同一类结论（优势或某类缺口）的“准确 / 不准确”会带到新版本。结论类型变了就不再沿用。
- **学习任务**：已开始、已完成或已跳过的任务保留；新计划里同名的任务不重复添加；未动过的任务按新计划重建。
- 已完成的任务可以撤销，改回待完成。

### 6.4 岗位要求确认页

- 可以添加、删除要求（3–30 条，每条最多 500 字），也可以修改类别。类别决定这条要求计入哪个维度：技能、经验、学历、限制条件、岗位职责、加分项。
- 解析冲突会显示出来，例如“没有识别出岗位名称”“只识别出 2 条要求”。确认后冲突清空。
- 后端会校验类别、优先级、条数和长度。
- 用链接导入岗位时，按段落、换行和列表项保留行结构，列表项会变成 `- ` 开头的行，这样要求解析能识别出来。之前整页文字会被压成一行。
- 返回“选简历”这一步时会重新读取简历列表，并区分“读取中”“读取失败（可重试）”和“确实没有简历”。
