## 2. 三份计划如何配合

三份折子各管一段，不得越权，也不得各干各的。

```text
本约定（调度）
  管：门禁、角色、并行、开工口令、交接仪式、回滚、禁止事项检查
  不管：怎么实现某个用例、画哪张页面、设计哪张表

后端实施计划（切片实现）
  管：S0→S5 每刀对象、不变量、事件、失败处理、最小表原则、可运行契约范围、验收门
  不管：Vue 页面、工作区视觉、未到该刀的库表

前端实施计划（页面交接）
  管：过门后开哪些工作区、已确认操作与禁止入口、九态验收、elite-web-designer 准召时机
  不管：库表、正式 API 字段清单、后端模块内部实现
```

| 问题 | 查哪份 |
| --- | --- |
| 现在能不能写代码？先做谁？能否并行？切片失败怎么办？ | **本约定** |
| 这一刀后端做什么、交什么、验什么？ | **后端实施计划** 第 3–4、6、9 章 |
| 这一刀前端开哪些工作区、禁止哪些按钮、何时召设计师？ | **前端实施计划** 第 3–6、9 章 |
| 状态、权限、禁止假设、已确认操作？ | **确认记录**（改规则必须先改它，见第 5.3 节） |

调度官拆边界、锁文件、宣布「可交接 / 可进入下一刀」、收冲突、组织回滚。后端切片官不写页面。前端工作区官不设计库表、不发明 API。契约守卫不写业务代码。

## 3. 一次一刀：切片军令

顺序抄两份计划，不得跳步，不得把 P0B 绑上：

```text
S0 基础底座
  -> S1 用户画像与能力证据
  -> S2 JD 文本导入与单岗位匹配
  -> S3 简历版本与投递
  -> S4 面试记录与基础复盘
  -> S5 登录后的求职工作台（只读汇总）
```

**一刀的完整生命周期（冻结之后）：**

```text
调度官宣布「本刀后端开工」
  -> 后端切片官按后端计划做本切片真实闭环
  -> 交接仪式（第 4 节）通过
  -> 调度官宣布「本刀前端可开工」
  -> 前端工作区官按前端计划只接本切片页面
  -> 单切片联调可演示
  -> 调度官宣布「本刀收兵」
  -> 才许下一刀后端开工
```

禁止把「S0 前端」和「S1 后端」叠在同一时段。禁止一刀未收兵就铺下一刀的表或页面。

## 4. 每个切片的交接仪式

仪式不过，前端不得开该切片页面，下一刀后端不得动土。

### 4.1 仪式步骤（每刀相同）

1. **后端切片官呈上三件**（后端计划 5.3，缺一件即停）：
   - 本切片**可运行 API**：本地能打通本切片命令 / 查询 / 长任务（若本刀有任务）。
   - 本切片**契约说明**：操作、权限、状态、错误语义（用户可修正 / 权限禁止 / 状态冲突 / 依赖失败 / 系统故障）、事件；按切片增量，不写全集大表、不从页面字段反推。
   - 本切片**验收门对照**：后端计划第 4 章该刀表格；写清已演示与未演示。无证据不得称完成。
2. **契约守卫核对**：未发明确认记录没有的状态、权重、自动流转、事件名、业务对象或按钮；未放宽禁止假设；写命令含对象版本 / 冲突语义（该刀契约需要时）；长任务含任务 ID、可查询状态、失败原因、取消 / 重试是否按确认记录第二轮。
3. **禁止事项检查**核销第 9 节清单：无 P0B/P1/P2 入口与表、无 Python 运行方式、无敏感凭据入仓、无正式 Mock 主路径、无同文件并行脏合。
4. **调度官**口头或书面宣布：「Sx 后端可交接」。没有这句，前端按兵不动。
5. **前端工作区官**只开该切片工作区，只挂已确认操作；服务端是事实来源，不得用本地态覆盖正式状态，不得靠藏按钮代替鉴权。
6. 单切片联调按该刀验收门与前端九态清单演示。通过后调度官宣布「Sx 闭环可演示」，才开 S(x+1) 后端。

前端发现未确认字段、状态、权限、异常或模块影响：停该切片前端，缺口退回 P3.5，**先改确认记录**（及既有协同规则要求的 PRD 第 25 章、架构第 24 章），再评估两份实施计划受影响的切片。禁止为联调「先做一个没确认的按钮」。

### 4.3 前端准召 elite-web-designer 的时机

同时满足才准召，一次只交**一个工作区**：

1. 该切片后端已过第 4.1 节仪式。
2. 设计师只处理页面方案、视觉与交互，**不设计业务规则**。JD / 匹配仍只准确认记录第 4 节意图。

未过门：连愿景采集都不必开。本约定不安排现在做探索稿编码。冻结后也不把正式 Mock 工程当默认路径。

用户或实现要改**已确认**规则时，顺序锁死：

1. 先改确认记录（以及既有规则要求的 CRUD / 映射 / 权限 / 状态 / 模块交互表，PRD 第 25 章、架构第 24 章）。
2. 再由调度官评估：哪一刀后端、哪一页前端失效。
3. 再改实施计划（若步骤变了），最后才改代码。
4. 未走完 1–3，任何切片官 / 工作区官不得在实现里改语义。

禁止假设项（确认记录第 5、8、14 节等）进入页面、接口、数据库或代码。守卫见到即喝停。

## 6. 并行规则

摘全局规则第 15 条，并加上本约定的切片锁。

### 6.1 可以并行

- **调研、读档、验收对照、整理缺口清单**：不改同一实现文件即可并行。
- **不同文件的只读核查**：例如一人对确认记录、一人对后端计划验收门，只出报告。
- **同一切片、后端已可交接之后**，前端多个工作区官可并行，**前提是文件范围隔离**（例如 S0 的 identity 与 notification 不碰同一路由总表）。共享文件仍须加锁串行。
- 「不同切片且不同文件」在**文件物理上**互不碰撞，但被第 6.2 条军令压过：P0A 执行期**不准**用这条理由同时开 Sx 前端与 S(x+1) 后端。

### 6.2 禁止并行（硬）

- **同一文件**两名及以上智能体同时改。父 POM、`application.yml`、安全配置、共享内核、事件发布器、路由总表、App Shell、公共类型、设计令牌尤甚。
- **一次一个切片**：未宣布 Sx 收兵，不得开 S(x+1) 的正式表、API、页面。
- **不准同时开 S0 前端和 S1 后端**（推广：不准 Sx 前端与 S(x+1) 后端叠工）。即使文件不同，也禁止。
- 不准 S0 前端与 S0 后端抢写尚未交接的契约文件。前端只消费已交契约。
- S2 内不准两使同时改 Job 模块；S3 内不准 Resume 与 CRM 两使同时改引用。
- 不准派「P0B 使」与 P0A 使同时铺货。
- 需求已冻结、有计划、有回滚方案时，仍禁止盲目并行写代码；必须按刀宣布。

发现并行碰同一文件：立即停写，调度官收 diff，以先锁或调度官裁定为准，不得各写各的硬合。

## 8. 回滚：切片失败不进入下一刀

### 8.1 失败即停

下列任一发生，**不宣布收兵，不准下一刀**：

- 本切片可运行 API 打不通，或契约说明与确认记录不一致。
- 验收门无证据，或禁止假设被实现放行。
- 前端出现未确认按钮 / 字段 / 状态，或用页面倒逼改契约。
- 同文件并行脏合、范围胀到 P0B/P1/P2、用 Python 作为项目运行方式。
- 核心状态机被改歪、接口与已确认契约差太大、库表方向错误。

处置：停写 → 调度官决定回滚或最小修复当前刀 → 重新走交接仪式。**禁止带着缺口开下一刀「先往前赶」。**

### 8.2 回滚原则（摘全局规则第 16 条与后端计划 7.2，不新定恢复算法）

1. 建议全程 Git。大改前单独分支。每刀收兵记检查点。
2. 优先回滚而不是硬修：新功能破坏已闭环切片、UI 大面积发明操作、接口与契约差太大、库表方向错误、核心流程破坏、偏离计划去实现 P0B。
3. 未冻结就被误执行：立即停写，回滚已提交的接口 / 表 / 代码 / 页面，回到「只保留文书」。
4. P0B 若被误开，必须能单独关闭且不影响 P0A 主链。
5. 数据变更方向（扩展 → 迁移 → 收缩）、Worker 安全点、恢复优先级 A→E：以架构与后端计划为准，本约定不另立法。

### 8.3 冻结后陛下改规则

先走第 5.4 节契约守卫流程。宁可回退该切片，不在实现里硬改语义。
