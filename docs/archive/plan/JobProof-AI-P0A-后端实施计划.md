### 1.3 本折要办成什么

冻结后，按 S0 → S1 → S2 → S3 → S4 → S5，用已选定技术栈做出 P0A 后端真实闭环，使一个新用户可以只靠主动输入走通：

**画像与证据 → 粘贴 JD → 单岗位可解释匹配 → 冻结简历版本 → 创建投递并手动改阶段 → 记录面试轮次 → 基础复盘确认 → 工作台只读汇总。**

对应 PRD 第 22.1 节退出条件与第 23.1 节 P0A 验收。不自动外发，不依赖付费外部企业数据。

### 1.4 用户与终端（摘确认记录，不新定）

- 首发用户：大学生、应届毕业生及毕业三年内早期职业用户。
- 桌面 Web 是完整工作端；移动 Web 只做查看、提醒和简单操作。App、浏览器扩展不进 P0A。
- 工作台是登录后的求职工作台，不是营销官网。工作台只锁定**读取边界**，不冻结卡片、排序、快捷操作。

### 1.5 技术方向（已选定，本折不重开选型）

技术选型已比过三条路，本折只沿用，不另起炉灶：

| 方向 | 组成 | 本折态度 |
| --- | --- | --- |
| A. Vue + Java 模块化单体 | Vue 3 Web；Java 17 + Spring Boot 3 API；独立 Worker；MySQL 8；Redis；S3 兼容存储 | **已选主路，本折只写后端这一半** |
| B. React + NestJS | 全 TypeScript 单体 | 候选，不进 P0A |
| C. 事件驱动微服务 | 多服务 + 消息平台 | P0A 不采用；不引入 Kafka |

后端运行方式固定为：

- Java 17 + Spring Boot 3 **模块化单体**
- **独立 Worker**（Redis 队列）做长任务
- MySQL 8、Redis、S3 兼容对象存储
- AI 只走 Java Provider Adapter 逻辑端口（`structuredGenerate`、`extractDocument`、`classifyAndScore` 等，见技术选型 7.1）；不绑死具体模型供应商
- **禁止 Python 作为项目运行方式**
- **Vue / 页面 / 组件不归工部本折编写**

分层按架构第 6 章：应用用例编排命令与事务；领域层守状态机与不变量；基础设施才碰数据库、队列、文件和供应商 SDK。模块之间不得直接写对方库表，不得循环依赖。

## 4. 各切片：对象、不变量、事件、失败处理、验收门

以下只摘确认记录与架构已登记内容。**不发明新规则、新状态、新事件名。** 库表只允许「本切片对象的最小必要」，到该切片开工时再设计，本折不画全库。

事件名取自架构第 11.2 节候选目录。确认记录已把写入范围说清的，按确认记录执行；架构里仍标「待确认」但确认记录第 11.2 / 13.5 节已写明的复盘确认，以确认记录为准，不另造事件。

长任务通用状态（确认记录 4.1 / 11.2 / 12.4）：`PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`、`CANCELLED`。

取消与重试（确认记录 4.5；简历定制、复盘分析、导出任务「规则同第二轮」）：

- `PENDING` 可取消，不计入模型用量。
- `RUNNING` 可取消，任务为 `CANCELLED`，已发生的模型调用计入用量，不生成成功结果。
- `SUCCEEDED`、`FAILED`、`CANCELLED` 不可再取消；再做必须开新任务。
- 超时、连接失败、短暂 5xx：**最多自动重试 2 次**。
- 结构校验失败、非 JD、超长超短、内容安全失败：**不自动重试**，只允许用户修正后手动重试。
- 手动重试不改写已成功历史任务，只创建新任务。

### 4.1 S0 基础底座

**主要模块：** Identity、Data Rights、Task、Notification、Audit。

**本刀对象：**

| 对象 | 拥有模块 | 状态（已确认） | 关键操作 |
| --- | --- | --- | --- |
| 账号 / 会话 | Identity | 会话有效 / 退出 / 改密后全部失效 | 邮箱注册登录；邮箱验证码重置密码；退出当前会话；改密；注销进入删除编排 |
| 导出任务 | Data Rights + Task | 同长任务五态；下载限时，过期作废 | 本人发起导出 |
| 删除请求 | Data Rights | 已提交、处理中、部分受限、已完成、失败 | 对象级或账号级彻底删除申请 |
| 通知 | Notification | `待发送 -> 已送达 -> 已读`；另有 `发送失败`、`已过期`、`已归档` | 系统按事件生成；用户单条或批量已读 |
| 审计记录 | Audit | 只留必要痕迹 | 安全与数据权利相关操作留痕；运营默认不看原文 |

**关键不变量（确认记录 12.1、12.4、11.3）：**

1. P0A 唯一登录：邮箱 + 密码。无手机号、第三方、MFA。
2. 会话：服务端会话 + HttpOnly Cookie。退出只结束当前会话；**修改密码后全部会话失效**。
3. 注销不立即物理删除，进入数据删除编排。
4. 导出范围只含：账号、画像正式事实、证据元数据与本人文件、简历主档与冻结版本、投递时间线、面试轮次、已确认复盘。不含他人数据、运营内部审计、供应商原始日志。
5. 常规整理用归档。彻底删除走数据权利；提交前展示关联影响、不可逆说明和法定例外入口。法定年限不在 P0A 锁死；处理中可「部分受限」，例外走合规工单。P0A 不实现完整运营后台。
6. 仅站内通知。类型只许：任务完成、任务失败、面试提醒（轮次 `已安排` 且有时间）、数据导出 / 删除进度、安全与数据权利。不做 Offer 截止提醒。
7. 站内写入成功即 `已送达`。同一业务事件 ID + 类型 + 接收人幂等去重。
8. 通知失败不回滚业务，也不重复触发投递、外发、Offer 接受或删除。
9. 安全、授权和数据权利通知不可完全关闭。
10. 分享底座：默认只读、限时、可撤销（确认记录 7.2.14、PRD 9.15）。导师默认不进 P0A 编辑。

**事件（架构 11.2，本刀先接通通道）：**

| 事件 | 产生 | 消费 | 失败 |
| --- | --- | --- | --- |
| AuthorizationRevoked | Data Rights | 各敏感模块 | 立即阻止新处理；清理失败进补偿 |
| DeletionRequested | Data Rights | 各数据模块、Audit | 汇总回执；部分失败不得显示全部完成 |
| TaskCompleted / TaskFailed | Task | Notification、业务模块 | 去重；不含敏感正文 |
| NotificationRequested | 各业务模块 | Notification | 渠道失败不回滚业务 |

S0 先把外盒发布、幂等消费、对象级授权和私有文件短时签名 Spike 跑通。后续切片只往这套通道挂，不另起一套队列。

**失败处理：**

| 场景 | 系统行为 | 禁止 |
| --- | --- | --- |
| 邮箱未验证改密 | 验证码失败则拒绝 | 无验证改密 |
| 导出过期 | 链接作废 | 永久裸链 |
| 导出成功 / 删除部分失败 | 进度可见 | 未完成显示全部完成 |
| 通知失败 | 业务状态不变 | 用通知重试重做投递 / 删除 / 接受 Offer |
| 同一事件重复投递 | 不生成第二条有效通知 | 叠通知 |
| Worker 重复消费 | 不产生重复业务结果 | 无幂等键硬写 |

**本刀最小库表原则：** 只为账号、会话、任务技术表、通知、删除 / 导出请求、审计索引建最小表。不为画像、JD、简历、投递预建「未来大表」。文件走 S3 兼容私有桶，库里只留引用，不落密钥。

**本刀可运行契约（交给前端之前必须有，但仍等冻结后才写）：** 注册、登录、退出、改密、重置密码、当前用户、发起导出、查询导出 / 删除进度、通知列表与已读。只说明命令 / 查询语义、权限、错误类别（用户可修正 / 权限禁止 / 状态冲突 / 依赖失败 / 系统故障），不在本折里写路由和字段清单。

**验收门：**

| 门 | 来源 | 通过标准 |
| --- | --- | --- |
| MOCK-AUTH-001 | 确认记录 13.6 | 邮箱登录 / 改密；改密后旧会话失效 |
| MOCK-DATA-002 | 确认记录 13.6 | 导出成功或删除部分失败时进度可见，不得提前显示完成 |

### 4.2 S1 画像与能力证据

**主要模块：** Profile、Evidence。依赖 S0 的当前用户、对象授权、文件与删除编排回执。

**本刀对象：**

| 对象 | 拥有模块 | 要点 |

**关键不变量（确认记录第 3 节、12.2、12.3）：**

1. 正式匹配前必须确认**当前求职方向**。缺失字段保持未知，不生成默认事实。
2. 只有用户主动填写或确认后，才成为正式画像事实。被拒绝候选不得进入正式匹配和简历生成。
3. 建议补、缺失保持未知：最高学历、毕业时间、专业、目标城市、工作方式、现实限制（不接受的城市 / 出差 / 夜班 / 销售 / 加班 / 行业，可明确「无限制」）。

5. 不采集、不用于匹配：性别、年龄、民族、婚育、政治面貌、身份证号、家庭住址。
6. 完整度：有求职方向即可匹配，完成度至少记 30%；第 3 条六项每填一项约 +8%；技能或年限可补到 100%。
7. 证据强度：强 = 可核验材料（100）；中 = 项目或实习描述且用户确认、无独立核验件（70）；弱 = 仅自述（40）。无材料自述 = 待补证，不写「能力不足」。

9. 已归档证据可恢复。删除失败保留可重试状态。
10. 有效简历版本引用的证据不能直接删除，只能归档（第 3 节；与第 8 条一致）。
11. 仅本人可编辑。运营默认不看原文。导师默认不进 P0A。

### 4.3 S2 JD 与单岗位匹配

**主要模块：** Job、Matching。只读 Profile 已确认事实、允许使用的证据、`CONFIRMED` 岗位版本、已发布匹配规则版本。

**本刀对象：**

| 对象 | 状态（已确认） |
| --- | --- |
| JD 原文快照 | 保留原文；过短过长或非 JD 不创建解析成功结果 |
| 解析任务 | `PENDING` / `RUNNING` / `SUCCEEDED` / `FAILED` / `CANCELLED` |
| 岗位版本 | `DRAFT`、`REVIEW_REQUIRED`、`CONFIRMED`、`ARCHIVED` |
| 匹配任务 | 与解析任务同一套任务态 |
| 匹配报告 | `CURRENT`、`STALE`、`ARCHIVED` |

P0A 由用户**粘贴 JD 文本**。正式匹配前至少确认：岗位名称、主要职责、硬性技能、经验要求、学历要求、地点、工作方式。未提供的薪资、福利等保持未知。

**关键不变量（确认记录第 4 节，一条不改）：**

1. AI 解析只是候选；用户确认后才成正式岗位事实。
2. 匹配报告必须可解释：总分、分项、加分项、扣分项、缺失项、对应证据、AI / 规则依据、置信信息、未知项。
3. 任务、岗位版本、匹配报告分三套状态。输入变化时，已成功历史任务保持 `SUCCEEDED`，旧报告 `CURRENT` → `STALE`，重算创建新任务和新报告。
4. 「证据门槛 + 规则分」。硬性要求先做门槛；普通要求按证据有无和强弱计分；未知项单独列出；加分项不能掩盖硬性缺口；**AI 只对照证据，公开规则算分**。不得模型先出总分再补解释。
5. 四维公开权重（百分制相加 100）：硬性门槛 30、技能与证据 35、经历相关 25、限制符合 10。普通用户不能改权重。不把薪资、企业风险、回复率、敏感属性做成维度。
6. 等级：`高度匹配`、`部分匹配`、`缺口明显`、`无法判断`。
7. 硬性缺口只统计「已确认不满足」，未知不当成缺口。缺口计数：学历、地点、工作方式各 1；被标硬性的经验要求不满足算 1；硬性技能整体算 1（任一已确认硬性技能不满足即计 1，不按技能个数累加）。
8. 1 个已确认硬性缺口：报告最高 `部分匹配`。2 个及以上：最高 `缺口明显`。加分项不能抬过该上限，也不能把 `无法判断` 改成其他等级。
9. 未知项不打 0 分，也不算符合。该维只对已判断项计分（缩小分母），并列出未知项。
10. 用户未设任何限制时，限制符合维不参与加权，其 10% 按 30:35:25 重分到其余三维。
11. 仅当求职方向缺失，或 7 个正式匹配确认字段中有 4 个及以上为未知、无法形成有效对照时，整份报告为 `无法判断`。不得因单个未知字段把整份打成 `无法判断`。
12. 证据强弱换算只用于技能与证据、经历相关中已判断项：强 100、中 70、弱 40；自述无证据不进分母、标「待补证」、不得写成「能力不足」；明确不具备为 0，若是硬性技能同时构成硬性缺口；双方都未提及为未知、不进分母。
13. 维内得分 = 该维已判断项得分的算术平均。硬性门槛：满足 100，不满足 0，未知不进分母。
14. 总分 = 各维按当时生效权重加权，0–100，先算分再套等级上限。
15. 无硬性缺口：≥80 `高度匹配`，60–79 `部分匹配`，低于 60 `缺口明显`。有硬性缺口时先套第 8 条上限，再与分数映射取更低者。
16. 加分项最多给总分 +5，且不能突破第 8 条，也不能改变 `无法判断`。
17. 置信度：无未知对照项为高；有未知但已判断项不少于一半为中；已判断项不足一半但仍能出分为低。`无法判断` 时不展示误导性高置信度。
18. JD 文本最短 80 字、最长 20000 字。先空白压缩和明显样板清洗，不补造岗位内容。
19. 非 JD：解析 `FAILED`，允许改文本后重发。多岗位混合：不自动拆成多个匹配，提示只确认其中一个岗位后再匹配。
20. 重复识别：规范化后全文相同 → 复用已有原文快照和岗位版本，不新建岗位；公司名和岗位名称相同但正文有变化 → 提示可能重复，由用户选择并入已有岗位并生成新版本，或创建新岗位；岗位名称相同、公司不同 → 不同岗位。除全文相同外，不得自动合并。
21. `STALE` 默认可查看、可与新 `CURRENT` 对比，不自动归档。用户可主动归档。P0A 不提供报告物理删除按钮。
22. Matching **不得改** Profile、Evidence、Job 或投递状态。
23. 匹配失败、取消或 `无法判断` 都不得自动创建投递、取消投递或改简历。
24. 已发布匹配规则版本：P0A 可预置一条已发布规则快照供 Matching 只读。**不建设运营发布后台。** 不得另设权重。

**事件：**

| 事件 | 产生 | 消费 | 失败 |
| --- | --- | --- | --- |
| JobImported | Job | Task、Audit | 失败原因保留；重试按解析任务契约 |
| JobParsed | Job | Matching | P0A 不得据此启动综合风险；消费幂等 |
| ProfileSnapshotChanged / EvidenceChanged / 岗位确认变化 | 上游 | Matching | 只把相关 `CURRENT` 转为 `STALE`，不自动重算 |
| TaskCompleted / TaskFailed | Task | Notification、Job / Matching | 去重；不写敏感正文 |

**失败处理：**

| 场景 | 系统行为 | 禁止 |
| --- | --- | --- |
| 过短 / 过长 | 不创建解析成功结果，保留原文和失败原因 | 补造岗位内容 |
| 非 JD | 解析 `FAILED` | 当成正式岗位 |
| 多岗位混合 | 不自动拆多个匹配 | 默默拆成多岗 |
| 非全文相同 | 不得自动合并 | 后台擅自并岗 |

| 输入变化 | 历史任务仍 `SUCCEEDED`，旧报告 `STALE` | 改写历史任务态 |

**本刀最小库表原则：** 只加 JD 原文、解析任务、岗位版本、匹配任务、匹配报告及分项解释所需最小结构。规则版本可用预置只读记录。不建收藏表、风险表、简历表、投递表。

**本刀可运行契约：** 粘贴导入、查询解析任务、确认 / 校正岗位版本、发起匹配、取消 / 手动重试、读当前报告、读 STALE 并对比、归档报告。报告字段必须能装下第 2 条必解释项。

### 4.4 S3 简历与投递 CRM

**主要模块：** Resume、Application CRM。方向为**流程管控型**（确认记录第 6 节）。

**本刀对象：**

| 对象 | 状态 |
| --- | --- |
| 简历主档 | `草稿 -> 待确认 -> 可投递 -> 已归档`；已归档可恢复为归档前状态 |
| 简历版本 | `生成中 -> 待用户确认 -> 已冻结 -> 已绑定投递 -> 已归档` |
| 投递 | 主链 `待投递 -> 已投递 -> 已查看 -> 笔试 -> 面试中 -> 已获Offer -> Offer已接受 / Offer已拒绝`；终止态 `主动放弃`、`招聘方拒绝`、`岗位关闭`、`长期无回复`、`接受后撤回`。不设独立「结束」 |

**关键不变量（确认记录第 7、10 节）：**

1. 只有本人可创建、编辑、复制、归档、恢复自己的主档。运营默认不能看原文。被分享人只读。
2. 创建方式：空白、模板（软件开发、测试、数据分析、产品）、已有简历文本导入。导入和 AI 生成先入候选，主档变 `待确认`；用户确认或删除候选后，才能回 `草稿` 或进 `可投递`。
3. 主档可编辑教育、经历、项目、技能、证书和自我介绍。AI 改写 / 压缩 / 扩写 / 纠错只出候选。
4. 不得虚构公司、时间、项目、角色、成果数字、证书或技术经历。无来源数字必须改成定性描述或标待补证。
5. P0A 不提供主档物理删除按钮；彻底删除走数据权利。复制主档得新 `草稿`，不复制已绑定投递关系。
6. 只有主档为 `可投递` 时才能冻出 `已冻结` 版本。冻结后不可原地改；要改必须从主档再冻新版本。
7. 进入 `可投递` 和冻结前必须同时满足：没有未确认的 AI 事实；每条关键成果要么已关联允许使用的证据，要么用户逐条确认「暂无证据仍要冻结」。
8. 创建投递绑定一个 `已冻结` 或已是 `已绑定投递` 的版本，该版本转为 `已绑定投递`。已绑定版本不可覆盖、不可回滚内容。
9. 可对比两个版本。P0A 可从 `已冻结` 或 `已绑定投递` 导出 PDF。分享走数据权利。
10. AI 按已确认 JD 生成定制简历是异步任务，取消 / 重试同第二轮；成功后得到 `待用户确认` 版本，**不得直接变成 `已冻结`**。
11. 收藏不进 P0A。创建投递不会由收藏或匹配自动触发。匹配报告**不是**创建投递的前置。
12. 「准备投递」建 `待投递`，或「记录已投递」建 `已投递`。两者都必须绑定：本人的 `已冻结` / `已绑定投递` 简历版本，以及 `CONFIRMED` 岗位版本。
13. 可记录渠道、投递时间、备注。公司名默认取自已确认 JD，用户可改备注名，**不因此改岗位快照**。招聘联系人、聊天附件不是 P0A 必填。
14. 允许前进与允许更正严格按确认记录 7.3.20–7.3.21。不能跳步乱改。`Offer已接受` 不能退回，只能走 `接受后撤回`（二次确认，展示可能影响；是终止态，不是 `主动放弃`）。
15. 每次状态变化记录操作者、时间、来源、前状态、后状态。系统不得根据聊天或外部平台自动改正式状态。
16. 并发用版本号校验，冲突时拒绝覆盖，保留双方内容让用户选择。
17. 归档不解除已绑定简历版本。P0A 不做批量改状态、批量导入、漏斗、收藏。
18. 进入 `面试中` **不强制**创建面试轮次。投递状态与轮次结果不自动互写。
19. 冻结：Resume 模块内强一致；校验 Evidence 引用；失败不产生半成品版本。
20. 创建投递：Application CRM 事务内引用已存在冻结版本和确认岗位；失败不改简历内容。绑定失败不创建投递。
21. 变更阶段：Application CRM 强一致 + 乐观并发；通知最终一致，通知失败不回滚投递。

**允许前进（照录 7.3.20，实现不得增减边）：**

- `待投递` → `已投递`、`主动放弃`
- `已投递` → `已查看`、`笔试`、`面试中`、`长期无回复`、`主动放弃`、`招聘方拒绝`、`岗位关闭`

**允许更正（照录 7.3.21，须记录原因）：**

### 4.5 S4 面试与基础复盘

**主要模块：** Interview、Review。P0A **不单独做「面试流程」状态机**，只做轮次；投递上的 `面试中` 表示该机会处于面试阶段。

**本刀对象：**

| 对象 | 状态 |
| --- | --- |
| 面试轮次 | `待安排 -> 已安排 -> 进行中 -> 已完成`，另有 `已取消` |
| 复盘报告 | `待生成 -> 分析中 -> 待确认 -> 已确认`，另有 `失败`、`已归档` |
| 建议项 | `待确认` / `已确认` / `已拒绝` |
| 分析任务 | 第二轮五态 |

**关键不变量（确认记录第 11、13 节）：**

1. 一轮次必须属于本人的一条投递。一条投递可以有 0 到多轮。进入 `面试中` 不强制创建轮次。
2. 类型：`HR初筛`、`一面`、`二面`、`终面`、`加面`、`其他`。选 `其他` 可写自定义名称。
3. 创建时无时间进 `待安排`，有时间进 `已安排`。
4. 允许前进：`待安排` → `已安排`、`已取消`；`已安排` → `进行中`、`已取消`，清空时间并填原因可回 `待安排`；`进行中` → `已完成`、`已取消`。
5. 允许更正（须填原因）：`已完成` 可回 `进行中`；`已取消` 可回取消前状态。不能跳步乱改。
6. 字段：类型 / 名称、计划时间（可空）、时区、结果、备注。结果：`待定`、`通过`、`未通过`、`待下次`。**结果不改投递状态，轮次完成也不自动改投递。**
7. 时区用用户时区，默认 `Asia/Shanghai`。无计划时间不得创建确定提醒。
8. 不采集录音、不转写、不接实时 Copilot。准备包和模拟面试属 P0B。
9. 仅本人可创建、编辑、取消。常规归档随投递归档；彻底删除走数据权利。并发用版本号，拒绝覆盖。
10. 轮次 `已完成` 可不自动创建复盘，只允许提示用户去复盘。
11. 一份复盘必须属于一条投递，可空关联一轮次。无轮次也可复盘。用户手动发起。
12. 输入：手写问答或粘贴文本。只读引用该投递绑定的简历版本和已确认岗位版本。
13. AI 只出候选：问题清单、回答问题、改进建议。不得添加虚假经历。
14. 用户点「完成本次复盘」后报告进 `已确认`；未处理建议视为不写入。已确认报告不覆盖改写，要补只能再开一份新复盘。
15. 只有用户确认的项才能写入「已确认改进项 / 弱项」。拒绝的不得进画像、匹配或简历。
16. 复盘不得改投递状态、轮次状态或正式技能等级。P0A 不生成训练任务，不回灌准备包。
17. 面试时间变更则更新或作废旧提醒，不叠两条有效提醒。无时间不建提醒。
18. 创建 / 改轮次：Interview 强一致 + 乐观并发；通知最终一致，失败不回滚轮次。
19. 生成复盘：任务最终一致；失败保留原因，不写弱项。确认弱项：Review 事务内写入已确认改进项；失败不部分写入该条。

**事件：**

| 事件 | 产生 | 消费 | 失败 |
| --- | --- | --- | --- |
| InterviewScheduled | Interview | Notification | 按事件和渠道去重；失败不回滚轮次 |
| InterviewRoundCompleted | Interview | Review（只作提示，禁止自动创建） | 不得据此改投递 |
| ReviewConfirmed | Review | Profile（仅已确认改进项） | 未确认不写；失败不部分写入该条 |
| TaskCompleted / TaskFailed | Task | Notification、Review | 去重 |

架构 11.2 曾注 ReviewConfirmed「写入范围待确认」。确认记录 11.2 / 13.5 已确认：**仅用户确认的那一条改进项**，未确认 / 已拒绝不进画像。本折不扩大写入范围，不另起事件名。

Interview / Review → Application CRM：**禁止回写投递主状态。**

**失败处理：**

| 场景 | 系统行为 | 禁止 |
| --- | --- | --- |
| 无时间建提醒 | 不创建确定提醒 | 捏造时间 |
| 复盘任务失败 | 报告 `失败`，保留原文 | 悄悄写弱项 |
| 未确认建议 | 保持候选 | 写入正式弱项 |
| 完成复盘时尚有未处理项 | 那些项不写入 | 默认全确认 |
| 逐条拒绝 | 不进画像 | 后台继续使用 |
| 轮次并发冲突 | 拒绝覆盖 | 后写覆盖 |
| 轮次填结果 / 完成 | 只改轮次 | 改投递主状态 |
| 通知失败 | 轮次保持 | 回滚轮次 |

**本刀最小库表原则：** 只加轮次、复盘报告、建议项、分析任务引用。不建录音、题库、准备包、训练任务表。

**本刀可运行契约：** 在投递下创建 / 改轮次、补时间、改状态、填结果备注、发起复盘、查询分析任务、逐条确认 / 拒绝、完成本次复盘、读已确认改进项。

| 门 | 来源 | 通过标准 |
| --- | --- | --- |

| MOCK-INTERVIEW-002 | 确认记录 13.6 | 已完成改结果，不改投递状态 |

### 4.6 S5 工作台只读汇总

**主要模块：** 不新建写入模块。用各模块只读查询组成工作台读取面。架构称 Web Workspace / Task UI Adapter；工部只提供**只读汇总查询**，不拥有业务状态。

**允许读取的对象（架构 6.3.1、技术选型 3.2，是数据边界不是卡片方案）：**

- 求职画像完成度
- 能力证据完成度
- 最近导入的 JD
- 当前单岗位匹配结果
- 当前简历版本
- 当前投递进度
- 即将进行的面试
- 待完成的面试复盘
- AI / 异步任务状态
- 当前待办

**关键不变量：**

1. 工作台只负责展示、导航和继续任务所需的读取；**所有写入必须打回对应领域模块**，S5 不得提供「工作台专用写接口」。

3. 卡片、排序、快捷操作**尚未冻结**。S5 不得把某一种卡片 JSON 写成业务契约。
4. 「当前待办」只聚合已有对象上的未完成事项（例如待确认候选、待确认复盘、已安排且有时间的轮次、失败任务）。**不新建独立待办聚合，不发明待办状态机。**
5. 公开宣传首页不纳入 P0A 主闭环验收。

**事件：** 不新造工作台事件。只读已有事件落地后的状态。

**失败处理：** 某一块读取失败时，只让该块失败，不得为了「首页好看」用默认事实填空（与「缺失不生成默认事实」一致）。不得因工作台查询改写任何业务状态。

**本刀最小库表原则：** **原则上不加新业务表。** 若查询过重，只允许只读投影且可重建，不得当唯一事实源（架构 17.4 恢复等级 E）。

**本刀可运行契约：** 一条或少数几条只读汇总查询，字段可追溯到上述对象；另可复用前序切片已有详情查询。入口必须能映射到已确认业务操作，不得多出未确认按钮背后的 API。

### 6.3 契约写法（原则，不是本折里的正式 OpenAPI）

摘架构 6.4，冻结后按切片增量写，不在本折展开路由：

1. 用户意图分成命令、查询、异步任务、事件，一接口不混多种语义。
2. 写命令带幂等信息和对象版本；返回已接受、已完成、冲突或失败。
3. 长任务立即回任务引用，结果用查询（轮询等协议到实现时再评，本折不锁 SSE / WebSocket）。
4. 列表必须分页、稳定排序、可追踪过滤。
5. 错误区分：用户可修正、权限禁止、状态冲突、依赖失败、系统故障、须人工处理。不暴露供应商堆栈。
6. 契约来自业务对象与已确认操作，不从页面字段反推。
