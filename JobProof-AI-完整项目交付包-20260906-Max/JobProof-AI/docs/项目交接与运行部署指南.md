# JobProof AI 项目交接、运行与部署指南

本文是交付包的权威操作入口。命令均从解压后的 `JobProof-AI` 根目录执行；路径可自由移动，不依赖原开发电脑的绝对路径。

## 1. 技术栈与端口

- 前端：Vue 3、TypeScript、Vite 8，Node.js `>=24.15.0 <25`，npm 11；交付验证版本为 Node.js 24.19.0。
- 后端：Java 17 目标、Spring Boot 3.5、Maven 3.8+，Flyway 管理数据库结构；本地可使用 JDK 17 或更高版本。
- 本地默认：前端 `127.0.0.1:5174`，后端 `127.0.0.1:18081`，H2 文件数据库和本地私有文件存储。
- 服务器 Compose：Nginx 公开 80/443；应用、Redis、MinIO、ClamAV 只在 Compose 网络中通信。

建议至少准备 4 GiB 内存。2 核 2 GiB 仅适合低流量试运行，完整栈容器上限合计 2780 MiB，详见 `docs/deployment-capacity-2c2g.md`。

## 2. 本地启动

### Windows

安装 JDK 17+、Node.js `>=24.15.0 <25` 和 npm 11。只有缺少交付 JAR、修改了后端源码或要求重建时才需要 Maven 3.8+。PowerShell 执行：

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\start-local.ps1
```

### Linux/macOS

安装同版本依赖和 `curl` 后执行：

```sh
chmod +x scripts/*.sh
./scripts/start-local.sh
```

脚本会检查 5174 和 18081 端口，缺少 `frontend/node_modules` 时执行 `npm ci`，缺少 `backend/target/jobproof-backend.jar` 时执行 `mvn -B verify`，然后启动两个后台进程。它会用命令行参数显式固定 `dev`、本地 H2/文件存储、开发验证码通道和下列测试账号，不继承接手者机器上的生产 profile。日志与 PID 只写入 `.local-run/`。

源码或锁文件修改后，Windows 使用 `.\scripts\start-local.ps1 -Rebuild`，Linux/macOS 使用 `./scripts/start-local.sh --rebuild`。普通重启优先使用已有 JAR；因此修改代码后不能省略重建参数，发布前还必须执行第 3 节的完整验证。

基础页面、登录和核心数据流只需要上述环境。完整本地文件能力另有系统依赖：Windows DOCX 模板预览使用 Microsoft Word COM，扫描版 PDF OCR 使用 Tesseract（含 `chi_sim`、`eng`）；生产 Docker 镜像已安装 LibreOffice、Tesseract 与中日韩字体。macOS 的默认开发配置没有经本项目验证的 Word/LibreOffice 预览桥，建议在 Docker/Linux 环境验收这些功能。

访问地址：<http://127.0.0.1:5174/>。后端健康检查：<http://127.0.0.1:18081/api/v1/health>。

停止：

```powershell
.\scripts\stop-local.ps1
```

或：

```sh
./scripts/stop-local.sh
```

本地数据位于 `backend/.local-data/`。需要全新数据库时，先停止项目，再自行备份并删除该目录；这会清空本地账号和业务数据。

### 本地账号

| 角色 | 登录名 | 密码 | 邮箱 |
| --- | --- | --- | --- |
| 管理员 | `admin` | `admin` | `admin@jobproof.local` |
| 求职者 | `seeker` | `seeker123` | `seeker@jobproof.local` |

固定账号由 `dev` 配置初始化，每次启动会恢复指定密码并使旧会话失效。它们不得出现在公网环境。

### 手工开发命令

后端：

```powershell
cd backend
mvn -B verify
java -jar target/jobproof-backend.jar --server.port=18081 --jobproof.storage.type=local --jobproof.cors.origins=http://127.0.0.1:5174
```

前端另开终端：

```powershell
cd frontend
npm ci
npm test
npm run dev -- --host 127.0.0.1 --port 5174
```

## 3. 修改后的完整验证

Windows：

```powershell
.\scripts\prepare-deployment.ps1
```

Linux/macOS：

```sh
./scripts/prepare-deployment.sh
```

该命令固定执行前端依赖安装、全部前端测试和生产构建，再执行后端 `mvn -B verify`，最后用本轮唯一构建产物重建 `deploy/web/`。任何一步失败都会停止，不应继续部署。

也可以分别执行：

```sh
cd frontend && npm ci && npm test && npm run build
cd ../backend && mvn -B verify
```

## 4. 服务器 HTTP 部署

HTTP 只用于内网、临时验收或申请证书前的引导，不应作为正式公网登录环境；正式公网发布继续执行第 6 节 HTTPS 流程。

运行服务器只要求 Docker Engine 和 Docker Compose v2。本交付已包含 Dockerfile 所需的 `backend/target/jobproof-backend.jar` 和 Nginx 所需的 `deploy/web/`，不修改源码时，服务器无需安装 Java、Maven、Node 或 npm。若接手者修改了源码，先在开发机或 CI 构建机按第 3 节重建并验证，再上传更新后的完整目录；不要在未经验证的生产服务器临时编译。

1. 上传整个 `JobProof-AI` 目录；不要上传旧 `.env`、数据库、日志或证书覆盖新服务器。
2. 进入 `deploy/`，把 `.env.example` 复制为 `.env`。
3. 将所有 `replace-with-*` 和示例地址改为目标环境真实值；禁止提交或回传 `.env`。
4. 至少把 `JOBPROOF_PUBLIC_ORIGIN` 改为实际的 `http://IP` 或 `http://域名`，并生成互不相同的 Redis、MinIO、HMAC 密钥。
5. `JOBPROOF_AI_MASTER_KEY` 必须是随机 32 字节的 Base64。Linux 可用 `openssl rand -base64 32`；PowerShell 可依次执行 `$bytes = New-Object byte[] 32`、`[Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)`、`[Convert]::ToBase64String($bytes)`。
6. 邮件、短信变量必须使用服务方签发的凭据。尚未接通验证码渠道时，把 `JOBPROOF_REGISTRATION_ENABLED=false`，只使用已初始化管理员验收。
7. 回到项目根目录运行 `./scripts/check-deployment-config.sh`；Windows 构建机可用 `.\scripts\check-deployment-config.ps1`。预检会拒绝占位符、缺失必填项和无效 Compose；PowerShell 版本还会确认 AI 主密钥恰为 32 字节。`docker compose config` 只验证语法，不代表密钥或业务已可用。
8. 检查并启动：

```sh
cd deploy
docker compose config --quiet
docker compose up -d --build
docker compose ps
curl -fsS http://127.0.0.1/healthz
curl -fsS http://127.0.0.1/actuator/health
```

ClamAV 首次启动会下载病毒库，可能需要数分钟。必须等 Redis、MinIO、ClamAV 和应用健康后再验收上传、模板预览、PDF、登录和注册。

生产 `.env` 以及 `deploy/data/`、Docker 命名卷均属于服务器状态，不在本交付包内。

## 5. 生产管理员初始化

生产配置明确关闭固定开发管理员，因此不存在可公开复用的“生产默认密码”。首次部署时按以下方式建立一个管理员：

1. 在 `deploy/.env` 中临时设置：

```dotenv
JOBPROOF_DEV_ADMIN_ENABLED=true
JOBPROOF_DEV_ADMIN_ALIAS=admin-bootstrap
JOBPROOF_DEV_ADMIN_EMAIL=owner@example.com
JOBPROOF_DEV_ADMIN_PASSWORD=替换为独立强密码
```

2. 只在受控维护窗口重新创建应用并观察启动日志：

```sh
docker compose up -d --build --force-recreate app
docker compose logs --tail=100 app
```

3. 使用 `owner@example.com` 和强密码登录，确认角色为管理员。
4. 立即把 `JOBPROOF_DEV_ADMIN_ENABLED=false`，并删除 `JOBPROOF_DEV_ADMIN_PASSWORD` 整行或把等号右侧设为空；确认后再执行：

```sh
docker compose up -d --force-recreate app
```

5. 再次使用邮箱登录。禁用初始化器后，临时别名不再可用，但已创建的管理员和密码仍保留。

此初始化器在启用时会在每次应用启动时重设管理员密码并注销旧会话，所以绝不能长期保持启用，也不能使用本地的 `admin/admin`。密码只能保存在受控密码管理器中。

## 6. HTTPS

正式公网环境应使用 HTTPS。证书首次签发、IP 短期证书限制、可信代理模型、续签和回滚见 `docs/https-deployment.md`。完成证书准备后使用组合编排：

```sh
cd deploy
docker compose -f docker-compose.yml -f docker-compose.https.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.https.yml up -d --build
```

必须设置实际的 `JOBPROOF_HTTPS_ORIGIN`，验证 HTTP 跳转、证书链、Secure Cookie、登录、注销、API、SSE 和麦克风权限。交付前只验证了配置与本地功能，未替接手者签发目标域名证书，也未在其服务器执行生产验收。

## 7. 备份、升级与回滚

备份：在维护窗口运行 `sh deploy/backup.sh`。它会短暂停止 app 与 MinIO，归档 H2 数据和 MinIO 对象；`.env`、证书和镜像需另行加密备份。完整边界与恢复演练见 `docs/backup-and-recovery.md`。

升级建议：

1. 备份当前应用数据、对象、`.env`、证书及当前代码/镜像版本。
2. 在独立目录解压新版本，比较 `.env.example`、Compose 和数据库迁移。
3. 运行完整验证及 `docker compose config --quiet`。
4. 在维护窗口构建并启动，检查 Flyway、健康状态与核心业务。
5. 保留旧 JAR、旧前端静态文件、旧 Compose 和兼容的数据备份作为回滚点。

不要在数据库迁移后只回滚代码并继续写入。必须先评估迁移的向后兼容性；不兼容时从维护窗口前备份恢复完整数据库与对象，并保持应用停止直至一致性验证完成。

## 8. 配置与数据安全

- `.env.example` 只有占位符，不是可直接用于生产的密钥文件。
- 不要把 `.env`、`letsencrypt/`、`data/`、`backups/`、日志或用户上传内容提交给开发者或源代码仓库。
- 应用、Redis、MinIO 和 ClamAV 不应直接暴露到公网；只公开 Nginx 80/443。
- 生产开启文件功能时必须保持 ClamAV 失败关闭策略，不能以静态文件检查替代恶意文件扫描。
- AI、SMTP、短信、域名和证书都需要接手方自己的供应商账号与密钥，本包不包含任何真实第三方凭据。

## 9. 目录与文档优先级

- `frontend/`、`backend/`：当前可执行源码和测试。
- `deploy/`：HTTP/HTTPS Compose、Nginx、备份和恢复验收脚本。
- `开发文档/`：产品需求、架构、技术选型和冻结业务契约。
- `docs/`：当前验收、安全、部署和历史实施记录。
- `ai对话功能全量开发/`：AI 简历对话工作台的专项开发资料。
- `JobProof-AI-工作台界面图-v1.0/`、`JobProof_AI_全栏目SVG图标库_v1/`：界面参考和图标资产。
- `简历模板/`：完整 Word 模板源库。

发生冲突时，运行行为以当前源码、数据库迁移和 Compose 为准；操作流程以本文和根 `README.md` 为准；`docs/plan/`、`docs/audits/` 中带日期的内容仅解释历史决策和当时验收状态。

## 10. 已知验收边界

交付构建会记录实际测试结果和 SHA-256 清单。当前本地前后端功能已独立验证；HTTP/HTTPS 的公网网络、真实 SMTP/短信/AI 凭据、目标服务器容量、正式证书签发和真实数据灾难恢复必须由接手方在自己的环境重新验收。`application-worker.yml` 是独立 Worker 骨架，正式部署继续使用默认的同进程 Worker。
